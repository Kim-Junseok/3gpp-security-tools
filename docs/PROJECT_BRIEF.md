## 1. 목표와 첫 버전의 결과물

사용자가 GUI에서 LTE/NR ciphering·integrity 알고리즘과 입력값을 선택·입력하고, 암호화·복호화, MAC 생성·검증, MAC-I를 붙인 뒤 암호화하거나 복호화 후 MAC-I를 검증한 결과를 확인하는 프로그램을 만든다.

첫 버전은 **사용자가 Python, WSL, 개발 도구 또는 별도 Python 패키지를 설치하지 않고 실행할 수 있는 Windows GUI 프로그램**이다. 공식 테스트 전체 통과와 GUI 실행 파일의 실제 동작을 모두 확인해야 첫 버전이 완성된 것으로 판단한다.

### 첫 버전의 필수 결과물

1. 다운로드 후 실행할 수 있는 Windows GUI 실행 파일 및 필요한 배포 구성.
2. 공개 Git 저장소의 구현 소스와 개발·빌드 방법.
3. 대상 알고리즘의 공식 테스트 입력 Set, 공식 기대값 Set.
4. 실제 구현으로 계산한 Answer Set과 알고리즘별 일치 결과.
5. 사용자 사용법, 지원 환경, 검증한 표준 버전, 알려진 제약을 포함한 README.

단일 .exe 파일 배포를 우선 검토한다. 의존 파일을 포함한 portable ZIP이 더 적절한 경우에는 실제 배포 형태를 명시하고 결정한다. 어느 형태든 사용자가 Python이나 라이브러리를 별도로 설치하도록 요구하지 않는다.

지원할 Windows 버전과 CPU 아키텍처는 패키징 전에 확정한다. Windows 10/11 x64는 검토할 후보이며, 지원 여부는 실제 시험 결과로 표시한다.

### 후속 목표

LLM이 자연어 요청을 도구 호출로 바꾸고, 실행 프로그램이 같은 계산 코어를 호출한 뒤 LLM이 결과를 설명하도록 확장한다. LLM 연결 자체는 첫 버전 완료 조건에 포함하지 않는다.

## 2. GUI·Python API·CLI·EXE의 역할

이 항목들은 서로 대체하는 구현 언어 선택지가 아니다.

| 용어 | 의미 | 이번 프로젝트에서의 위치 |
|---|---|---|
| GUI | 버튼, 입력창, 선택 목록으로 사용하는 화면 | 첫 버전의 사용자 인터페이스 |
| Python API | 다른 Python 코드가 함수를 호출하는 인터페이스 | GUI와 테스트가 공통 계산 코어를 호출하는 내부 경계 |
| CLI | 터미널에서 명령과 인자를 입력하는 인터페이스 | 개발·자동 검증에 필요할 때 추가; 사용자용 CLI 제품은 첫 버전 필수 아님 |
| .exe | Windows에서 실행하는 파일 형식 | GUI 프로그램의 배포 형태; .exe 확장자 자체가 GUI를 뜻하지는 않음 |
| LLM tool adapter | LLM의 호출 요청을 실제 함수 실행과 연결하는 코드 | 후속 단계 |

Python API는 인터넷 서버나 외부 유료 API를 의미하지 않는다. 같은 프로그램 안에서 GUI 코드가 계산 함수를 호출하는 것만으로도 Python API를 사용하는 것이다. 별도 pip 패키지 배포도 첫 버전 필수 사항이 아니다.

### 구조

| 구성 | 책임 |
|---|---|
| Core | ciphering·integrity 계산, 입력 범위 검증, 구조화된 결과·오류 반환 |
| GUI | 입력값 수집, 형식 선택·변환, Core 호출, 결과와 오류 표시 |
| 테스트 실행기 | 공식 벡터 읽기, Core 실행, 기대값 비교, Answer Set·보고서 생성 |
| 패키징 | GUI·Core·필요한 런타임과 의존성을 실행 가능한 형태로 묶음 |
| 후속 LLM adapter | 도구 호출 인자 검증, 동일 Core 호출, 결과 전달 |

- Core는 GUI widget, 터미널 입출력, LLM SDK에 의존하지 않는다.
- 계산 로직을 GUI 이벤트 처리 함수 안에 중복 구현하지 않는다.
- Core는 결과를 print만 하지 않고 객체로 반환한다.
- GUI, 테스트 실행기, 후속 LLM adapter는 동일한 계산 코어를 사용한다.
- GUI를 먼저 다 만들거나 Core만 완성하고 끝내지 않는다. 작은 입력·계산·출력 흐름을 일찍 연결하고 확장한다.

## 3. 알고리즘과 기능 범위

### 알고리즘 범위

“MVP” 대신 “1차 구현”이라는 표현을 사용한다.

| 대상 | 범위 | GUI 선택 번호 | 기반 |
|---|---|---|---|
| EEA0 / NEA0 | 1차 구현 | Ciphering 0 | Null |
| EIA0 / NIA0 | 1차 구현 | Integrity 0 | Null |
| 128-EEA1 / 128-NEA1 | 1차 구현 | Ciphering 1 | SNOW 3G |
| 128-EIA1 / 128-NIA1 | 1차 구현 | Integrity 1 | SNOW 3G |
| 128-EEA2 / 128-NEA2 | 1차 구현 | Ciphering 2 | AES |
| 128-EIA2 / 128-NIA2 | 1차 구현 | Integrity 2 | AES |
| 128-EEA3 / 128-NEA3 | 1차 구현 | Ciphering 3 | ZUC |
| 128-EIA3 / 128-NIA3 | 1차 구현 | Integrity 3 | ZUC |
| 256-NEA4 / 256-NIA4 | 후속: 전체 명세·공식 벡터 확보 후 | 4 계열, 지원 시 활성화 | SNOW 5G |
| 256-NEA5 / 256-NIA5 | 후속: 전체 명세·공식 벡터 확보 후 | 5 계열, 지원 시 활성화 | AES 기반 |
| 256-NEA6 / 256-NIA6 | 후속: 전체 명세·공식 벡터 확보 후 | 6 계열, 지원 시 활성화 | ZUC 기반 |
| 256-NCA4/5/6 | 제외 | 제공하지 않음 | AEAD |

- Ciphering 번호와 Integrity 번호를 각각 선택한다. 내부 식별자도 연산 종류와 번호를 함께 사용한다.
- GUI에는 숫자와 짧은 이름을 함께 보여준다. 예: “2 — AES (128-bit)”.
- LTE/NR 별도 선택 화면이나 별도 구현은 요구하지 않는다. 대응 이름은 문서에서 설명한다.
- 4~6은 알고리즘 계열 표시이며, 이를 모든 NAS/RRC IE의 wire encoding이라고 가정하지 않는다. 실제 IE encoding 검증은 이 도구의 범위 밖이다.
- 256-bit NEA/NIA는 정확한 명세와 공식 벡터가 확보되면 이어서 구현한다. 첫 버전에서는 미지원 상태를 명시하며 legacy 완성을 막지 않는다.

### 첫 버전 사용자 기능

| 기능 | 사용자 동작 | 결과 |
|---|---|---|
| 암호화 | Ciphering 알고리즘과 입력 지정 | Ciphertext |
| 복호화 | Ciphering 알고리즘과 암호문 지정 | Plaintext |
| MAC 생성 | Integrity 알고리즘과 입력 지정 | 계산된 MAC |
| MAC 검증 | Integrity 입력 및 비교할 MAC 지정 | 일치 여부와 계산된 MAC |
| MAC 생성 후 암호화 | Ciphering·Integrity 번호와 각각의 키, 입력 지정 | MAC-I를 붙인 데이터를 암호화한 최종 Ciphertext |
| 복호화 후 MAC 검증 | Ciphering·Integrity 번호와 각각의 키, 암호문 지정 | 복호화 데이터와 MAC-I 검증 결과 |
| Hex / Bit 입력·표시 변환 | 입력 형식을 선택하고 변환 | 동일한 데이터와 유효 bit 길이 |

위 표는 지원할 연산의 목록이다. 각 연산을 별도 화면이나 메뉴로 제공할 필요는 없으며, GUI는 송신·수신 탭과 보호 조합을 중심으로 구성한다.

기존 stream cipher/CTR 기반 ciphering은 같은 keystream XOR 연산으로 암호화와 복호화를 처리할 수 있다. GUI에서는 사용 목적을 알기 쉽도록 두 동작을 구분하되, 코어 구현은 공통화할 수 있다.

Null integrity는 실제 인증을 제공하지 않는다. GUI에서는 이를 “Null — 인증 보호 없음”으로 표시하고, MAC 비교 결과를 데이터의 인증 성공으로 표현하지 않는다.

### 암호화와 MAC의 동시 실행 — 첫 버전 필수

작성자의 추가 결정에 따라 독립 실행과 함께 **MAC 생성 후 암호화**를 제공한다. “동시 실행”은 한 번의 실행 버튼으로 다음 순서를 처리한다는 의미이다.

1. 선택한 Integrity 알고리즘으로 입력 데이터의 MAC-I를 계산한다.
2. 입력 데이터의 끝에 MAC-I를 붙인다.
3. 선택한 Ciphering 알고리즘으로 데이터와 MAC-I를 함께 암호화한다.
4. 최종 Ciphertext와 계산된 MAC-I를 구분하여 표시한다.

Cip=2, Itg=2의 계산 예시는 다음과 같다. `Data`는 사용자가 입력한 계산 대상 데이터이고, `||`는 bit 순서를 유지한 이어 붙이기이다.

```text
MAC-I = Itg2(K_int, COUNT, BEARER, DIRECTION, Data)
Ciphertext = Cip2(K_enc, COUNT, BEARER, DIRECTION, Data || MAC-I)
```

- Ciphering 번호와 Integrity 번호는 독립적으로 선택한다. 같은 번호여도 K_enc와 K_int는 별도 입력이며 같다고 가정하지 않는다.
- 이 연산에서는 COUNT·BEARER·DIRECTION을 두 계산에 공통으로 사용한다.
- 1차 legacy MAC-I는 32-bit이다. 입력이 L-bit이면 MAC 입력 길이는 L, ciphering 입력·출력 길이는 L+32이다. 길이는 프로그램이 자동 계산한다.
- 비정렬 Bit 입력에도 마지막 유효 bit 바로 뒤에 MAC-I를 붙인다. byte 경계에 맞추는 padding을 삽입하지 않는다.
- 최종 결과에서는 MAC-I도 암호화된다. Ciphertext 뒤에 평문 MAC-I를 다시 붙이지 않는다. 별도 MAC-I 표시는 검증용 중간 결과이다.
- 0~3 계열 조합을 지원하되 Null 동작은 해당 정의를 따른다. Cip0는 암호화 보호가 없고 Itg0는 인증 보호가 없음을 표시한다.
- 이는 독립 ciphering·integrity 알고리즘의 순차 실행이며, 제외한 AEAD/NCA 알고리즘을 추가하는 것이 아니다.
### 결합 수신 — 첫 버전 필수

이 도구의 결합 송신 출력에 대해 다음 과정을 한 번의 실행으로 처리한다.

1. 선택한 Ciphering 알고리즘과 K_enc로 암호문을 복호화한다.
2. 복호화 결과의 마지막 32-bit를 수신 MAC-I로 분리한다.
3. 나머지 원본 데이터에 선택한 Integrity 알고리즘과 K_int를 적용하여 MAC-I를 재계산한다.
4. 수신 MAC-I와 재계산 MAC-I를 비교하고 데이터 및 검증 결과를 표시한다.

- COUNT·BEARER·DIRECTION은 송신 때와 동일한 값을 입력받아 두 계산에 공통으로 사용한다. GUI의 송신/수신 탭과 무선 UL/DL DIRECTION은 별개이며, 수신 탭으로 바꾼다고 DIRECTION 값을 반전하지 않는다.
- 32-bit 분리는 1차 legacy 알고리즘의 규칙이다. 전체 입력 길이가 32-bit보다 짧으면 입력 오류로 처리한다.
- 비정렬 Bit 입력에서도 마지막 유효 32-bit를 분리하며 byte padding을 삽입하지 않는다. 분리 후 원본 데이터 길이는 프로그램이 자동 계산한다.
- MAC 검증 실패 시 복호화 데이터는 “검증 실패 데이터”로 표시한다. Core도 데이터와 함께 검증 상태를 반환한다.
- Null integrity는 인증 보호가 없음을 표시하고 인증 성공으로 표현하지 않는다.
- 임의의 NAS·PDCP 패킷을 자동 해석하는 수신 기능은 아니다. 아래 PDCP 적용 범위가 송신·수신 모두에 적용된다.

**PDCP 적용 범위:** 위 연산은 입력 데이터 전체를 MAC 계산 대상으로 삼고, `Data || MAC-I` 전체를 ciphering 대상으로 삼는 계산 기능이다. 실제 NR PDCP에서는 무결성 보호에 PDCP header가 포함되지만 ciphering 대상에서는 PDCP header가 제외되며, SDAP header 등에도 별도 규칙이 있다(TS 38.323 §5.8–5.9). 따라서 PDCP PDU 전체를 `Data`에 넣는 것만으로 표준 PDCP 결과가 재현된다고 표시하지 않는다. PDU 파싱과 보호 영역 자동 구성은 기존 범위 제외를 유지한다.

### 검증 기능과 사용자 기능의 구분

공식 테스트 전체 실행, 특정 알고리즘 테스트 선택 실행, Answer Set·보고서 생성은 개발·릴리스 검증의 필수 기능이다. GUI에 “테스트 실행” 버튼을 제공하는 것은 선택 사항이다.

### 이번 범위에 포함하지 않는 기능

- AEAD/NCA.
- NAS·PDCP PDU 파싱, SRB/DRB별 보호 영역 자동 구성, 보안 절차 재현.
- KDF·AKA·키 협상.
- LLM 연결, function calling 실행 루프, HTTP/MCP 서버.
- 사용자용 CLI 및 별도 Python 패키지 배포는 필수 결과물에서 제외.

## 4. GUI 입출력 요구사항

### GUI 사용 흐름

GUI는 송신 / 수신 탭으로 구분한다.

- 각 탭에서 Ciphering과 Integrity의 사용 여부 및 알고리즘 번호를 각각 선택한다.
- “사용 안 함”과 알고리즘 0(Null)은 구분한다. 사용 안 함은 해당 단계를 생략하고, 0은 해당 Null 알고리즘 정의를 적용한다.
- 선택한 조합에 필요한 입력 필드만 활성화한다. Null 알고리즘의 키 등 불필요한 입력은 요구하지 않는다.
- Ciphering과 Integrity를 함께 사용하면 각각 필요한 키를 입력받는다.
- 실행 버튼에는 현재 수행할 동작을 표시한다.
- Hex / Bit 선택은 입력·출력 영역에 제공한다.
- 최종 결과를 우선 표시하고 MAC-I 등의 중간 결과는 구분하여 표시한다.
- 두 기능을 모두 사용하지 않으면 실행 버튼을 비활성화한다.
- 구체적인 필드 배치와 중간 결과 표시 방식은 구현 시 결정한다.

| 보호 조합 | 송신 탭 | 수신 탭 |
|---|---|---|
| Ciphering만 사용 | 암호화 | 복호화 |
| Integrity만 사용 | MAC-I 생성 | 입력 데이터와 별도로 입력한 MAC-I 비교 |
| 둘 다 사용 | MAC-I 생성 → 데이터 뒤에 추가 → 암호화 | 복호화 → 마지막 MAC-I 분리 → 검증 |

결합 수신은 이 도구의 결합 송신 출력 형식을 기준으로 처리한다. Integrity만 사용하는 송신은 원본과 MAC-I를 구분하여 표시하며, 수신에서는 데이터와 비교할 MAC-I를 각각 입력받는다.

### 입력 항목

- 처리 방향: 송신 / 수신 탭으로 선택.
- Ciphering·Integrity 각각의 사용 여부와 알고리즘 번호.
- KEY, COUNT, BEARER, DIRECTION.
- 결합 송신·수신에서는 Ciphering·Integrity 번호와 K_enc·K_int를 각각 입력하고 COUNT·BEARER·DIRECTION은 공통으로 입력. Null 알고리즘에 불필요한 키는 요구하지 않음.
- 입력 데이터와 형식: Hex 또는 Bit.
- Integrity만 사용하는 수신에서는 비교할 MAC-I를 별도 입력. 결합 수신에서는 복호화 결과에서 MAC-I를 자동 분리.
- GUI에서 자동 계산된 데이터 bit 길이를 표시.

송신·수신 탭 내 세부 화면 구성은 구현 시 정하되, 선택한 연산에 필요한 필드를 명확하게 표시한다. COUNT·BEARER의 10진/16진 입력 형식을 화면에 명시하고 혼동 없이 해석한다. DIRECTION은 UL/DL 선택 방식이 권장된다.

### 데이터·키 형식

- Hex 및 Bit 입력에서 공백·탭·줄바꿈은 구분자로 무시한다.
- Hex는 byte 단위로 해석한다. 공백 제거 후 짝수 개의 hex digit만 허용하며 홀수 digit는 오류로 표시한다.
- 사용자 Hex 입력은 모든 byte를 사용한다. 길이는 byte 수 × 8로 자동 계산한다.
- Bit 입력은 0과 1만 허용하며, 실제 bit 수로 길이를 계산한다.
- 사용자가 LENGTH를 별도로 입력하지 않는다.
- KEY도 선택한 알고리즘의 키 길이를 만족해야 하며 앞쪽 0을 잃지 않도록 처리한다.
- Hex → Bit 변환은 각 byte를 8-bit로 표현하여 앞쪽 0을 보존한다.
- Bit → Hex 변환은 유효 길이가 8의 배수일 때만 허용한다. 그렇지 않으면 bit 표현을 유지하고, 길이가 바뀌는 padding을 자동 추가하지 않는다.
- 허용 범위를 벗어난 COUNT·BEARER·DIRECTION 또는 잘못된 데이터는 GUI에서 오류로 안내하고 Core에서도 검사한다.

### 공식 벡터 입력은 별도 규칙 사용

공식 테스트 실행기는 표준에 명시된 LENGTH를 읽어서 사용한다. 사용자 Hex 입력의 자동 길이 계산 규칙으로 덮어쓰지 않는다.

예: 공식 벡터가 32-byte buffer와 LENGTH=254를 제공하면 254-bit만 계산한다. Core는 이를 위해 데이터와 유효 bit 길이를 함께 받는다.

### 출력

- Ciphertext / plaintext / MAC과 유효 bit 길이.
- MAC 생성 후 암호화에서는 최종 Ciphertext와 검증용 MAC-I를 구분하고, 원본 길이와 MAC-I 포함 암호화 길이를 표시.
- 결합 수신에서는 MAC-I를 제외한 복호화 데이터와 유효 길이를 표시하고, 수신 MAC-I·재계산 MAC-I·검증 결과를 구분하여 표시.
- Byte 정렬 출력은 Hex와 Bit로 표시·복사 가능하게 한다.
- 비정렬 출력은 정확한 Bit 문자열을 기본으로 표시하며, 미사용 bit를 실제 결과로 포함하지 않는다.
- MAC 검증 결과와 잘못된 입력 오류를 구분한다.
- Core 결과는 JSON 직렬화 가능하게 구성하되, 첫 GUI에 JSON을 노출할 필요는 없다.
- 실행 오류, 미지원 알고리즘, 입력 오류, 테스트 벡터 미확보, 기대값 불일치를 내부적으로 구분한다.
- 앞쪽 0과 유효 길이를 보존하고, 화면 표시·복사 과정에서 계산 결과가 달라지지 않아야 한다.

### 256-bit 문서별 역할과 검증 범위

아래 9개 문서는 번호와 역할이 식별된 대상이다. 해당 버전의 원문·전체 테스트 벡터 확보와 검증 여부는 별도로 기록한다. 256-bit NEA/NIA는 기존 계획대로 후속 구현 대상으로 유지한다.

| 계열 / 문서에 포함된 알고리즘 | Document 1: algorithm specification | Document 2: implementation test data | Document 3: design conformance test data |
|---|---|---|---|
| SNOW 5G — 256-NEA4 / NIA4 / NCA4 | TS 35.240 | TS 35.241 | TS 35.242 |
| AES — 256-NEA5 / NIA5 / NCA5 | TS 35.243 | TS 35.244 | TS 35.245 |
| ZUC — 256-NEA6 / NIA6 / NCA6 | TS 35.246 | TS 35.247 | TS 35.248 |

- 각 계열의 Document 1을 알고리즘 구현 명세로 사용한다.
- Document 2와 Document 3의 NEA/NIA 관련 공식 테스트를 모두 검증 대상으로 등록한다. 한 종류의 테스트 문서만 통과한 상태를 전체 공식 테스트 통과로 표시하지 않는다.
- 각 문서는 NEA·NIA·NCA를 함께 다룬다. NEA/NIA 구현에 필요한 명세·테스트를 추출하고 NCA 전용 명세·테스트는 제외한다. NCA가 포함됐다는 이유로 문서 전체를 제외하지 않는다.
- 각 테스트에 implementation / design conformance 구분, 문서 번호·정확한 버전·절·원문 test set ID를 기록한다. 같은 데이터가 두 출처에 등장하면 출처 간 대응을 보존하고 집계 규칙을 명시한다.
- 구현 착수 시 9개 문서 각각의 고정 버전, 원문·벡터 확보 상태, NEA/NIA 대상 목록과 필수 총수를 기록한다. 기존 표의 “확보 필요”는 고정 버전 원문·벡터의 확보·검토가 필요하다는 의미이다. 자료 미확보는 BLOCKED로 표시한다.
- 256-bit의 입력 파라미터·MAC 길이·출력 형식은 해당 명세에서 확인한다. 앞서 정의한 legacy 32-bit MAC-I와 결합 연산 규칙을 자동으로 적용하지 않는다.

### 자료 확보와 공개

- 표준 원문을 둘 로컬 폴더를 미리 마련하고 Git 추적에서는 제외한다.
- 직접 다운로드할 수 없으면 정확한 문서 번호·버전·필요 형식을 작성자에게 요청한다.
- 자료 미확보는 BLOCKED로 기록한다. 해당 알고리즘을 검증 완료로 표시하지 않는다.
- Git에는 표준 링크와 정리한 벡터·기대값·계산 결과·비교 보고서를 공개한다. 벡터 공개 가능 범위는 출처의 배포 조건을 확인한다.
- 공식 expected Set은 원문에서 확보하고 actual Answer Set은 구현 실행으로 생성하여 서로 구분한다.
- Answer Set·보고서에는 코드 commit, 문서 버전, 실행 환경을 기록하여 어떤 구현의 결과인지 알 수 있게 한다.

### 변환 규칙과 검증 원칙

- 문서 번호·버전·절·원문 test set ID·출처 URL·입력·유효 bit 길이·기대 출력을 보존한다.
- Hex 공백·줄바꿈 제거, LENGTH 처리, 미사용 마지막 bit 비교 규칙은 공통 규칙으로 문서화한다.
- 공식 기대값을 구현 결과로 생성하지 않는다.
- 실패를 숨기는 skip·xfail·비교 길이 축소나 입력별 정답 하드코딩을 하지 않는다.
- 벡터 전사 오류 등을 수정할 때는 원문 근거를 남긴다.
- 자체 경계값·Null 동작·GUI 테스트는 공식 벡터와 별도 집계한다.
- 결합 송신·수신의 연결 검증도 자체 통합 테스트로 별도 집계한다. Cip2/Itg2 대표 사례, 서로 다른 키, 0~3 조합, 비정렬 bit 이어 붙이기, MAC-I 포함 암호화 길이를 확인한다. 결합 기대값은 검증 대상 연결 함수의 출력으로 만들지 않고 독립적인 참조 계산과 대조한다.
- 결합 송신→수신의 원본 복원과 MAC-I 일치를 확인하고, 데이터 영역·MAC-I 영역 각각의 변조에 대한 검증 실패, 32-bit 미만 입력 오류, 비정렬 bit 분리 및 Null 조합을 확인한다. 변조 검증 실패는 실제 integrity 알고리즘(1~3)을 대상으로 하며, 왕복 일치만으로 알고리즘 정확성을 판정하지 않는다.
- 일치율은 테스트 케이스 단위로 계산한다. 일부 bit만 맞는 경우 케이스 전체를 FAIL로 처리한다.
- “100% 통과”의 분모는 실행된 수가 아니라 사전에 확정한 필수 공식 케이스 수이다. 총수 0은 통과로 표시하지 않는다.

### 결과 보고

알고리즘 / Suite ID / 표준 버전 / 필수 총수 / PASS / FAIL / ERROR / SKIP / BLOCKED / 일치율.

각 실패에는 case ID, 기대값, 실제값, 유효 길이, 불일치 위치를 남긴다. 256-bit 후속 미지원 목록은 1차 공식 통과율과 구분하여 지원 범위를 명시한다.

## 6. 구현 기술과 Windows 배포

### Python 구현 방침

- Core는 Pure Python 우선이라는 작성자 방침을 유지한다.
- 외부 라이브러리는 배포·재사용 조건이 맞고 실행 파일에 함께 포함할 수 있는 경우 사용 가능하다.
- Python API는 라이브러리 종류가 아니라 호출 방식이므로 Pure Python 여부와 별개이다.
- 일부 Python 라이브러리가 C/C++ 확장을 포함할 수 있으므로, 이를 허용할지는 Pure Python 코어 방침과 별도로 결정한다. 기본 허용으로 가정하지 않는다.
- “사용자 추가 설치 없음”은 배포 요구사항이다. 개발 환경에서 라이브러리를 설치하는 것까지 금지하는 의미는 아니다.
- 재사용 라이브러리로 byte 비정렬 공식 벡터를 정확히 처리할 수 없다면 이를 보완하거나 대체 구현한다. 임의 padding은 허용하지 않는다.
- GUI framework는 아직 확정하지 않는다. Python 3.12.3 호환, Windows 패키징, 필요한 입력·표시 기능을 확인하여 선택한다.

### 실행 파일 제작

- WSL은 Core 개발과 테스트에 사용한다.
- Windows 실행 파일은 Windows Python 환경 또는 Windows CI runner에서 빌드·검증하는 방식으로 계획한다.
- PyInstaller는 패키징 후보이며, Python 런타임과 의존성을 묶어 사용자 추가 설치 없이 배포할 수 있다.
- PyInstaller는 cross-compiler가 아니므로 WSL/Linux 빌드 산출물을 Windows .exe로 사용할 수 있다고 가정하지 않는다.
- 패키징 도구·GUI framework·의존성 버전, 빌드 명령, 필요 리소스를 기록한다.
- 전체 알고리즘 개발이 끝나기 전에 최소 GUI와 대표 계산 경로로 Windows 실행 파일을 만들어 패키징 가능성을 확인한다.
- 개발 환경 테스트 통과와 배포 파일 동작은 별도로 검증한다.

패키징 참고: https://www.pyinstaller.org/en/stable/ 및 https://www.pyinstaller.org/en/stable/operating-mode.html

- [ ] 필수 공식 케이스 전부 PASS; FAIL / ERROR / SKIP / BLOCKED = 0.
- [ ] Null 동작을 별도 규칙 기반 테스트로 확인.
- [ ] 비정렬 bit·앞쪽 0·마지막 미사용 bit 처리 확인.
- [ ] 공식 expected Set, 실제 Answer Set, 100% 일치 보고서 준비.

### GUI 사용성
- [ ] GUI에서 알고리즘 선택, 입력, 암·복호화, MAC 생성·검증 가능.
- [ ] 한 번의 실행으로 MAC-I 생성 → 데이터 뒤에 추가 → MAC-I 포함 암호화 가능; Cip2/Itg2 대표 결과 및 지원 조합의 통합 테스트 통과.
- [ ] 송신·수신 탭과 보호 조합에 따라 필요한 입력 필드 및 실행 버튼 동작.
- [ ] 결합 수신의 복호화 → MAC-I 분리 → 검증 가능; 결합 송신 결과의 원본 복원 및 MAC-I 일치 확인.
- [ ] 실제 integrity 사용 시 데이터·MAC-I 변조를 검출하고 검증 실패 데이터로 표시.
- [ ] 32-bit 미만 입력 오류, 비정렬 bit 처리 및 Null의 인증 보호 없음 표시 확인.
- [ ] 사용자에게 별도 LENGTH 입력을 요구하지 않고 입력 형식에서 자동 계산.
- [ ] Hex/Bit 변환·결과 표시·복사가 유효 데이터와 길이를 보존.
- [ ] 잘못된 입력과 실행 오류를 화면에 명확히 표시.
- [ ] GUI 입력·변환·Core 전달 경로의 대표 사례를 테스트.
- [ ] GUI와 직접 Python 호출의 동일 입력 결과 일치.

### 배포
- [ ] 실제 지원 Windows 환경에서 배포 실행 파일이 열리고 GUI가 정상 표시.
- [ ] Python·WSL·개발 도구가 없는 환경에서 암·복호화와 MAC 동작 확인.
- [ ] 패키징된 프로그램이 사용하는 코어·의존성에 대한 공식 벡터 검증 경로 마련 및 실행.
- [ ] 다른 작업 폴더에서 실행해도 필요한 리소스 로딩 정상.
- [ ] 소스·테스트 데이터·Answer Set·보고서·사용법을 검토하고 GitHub Release 배포물 준비.
- [ ] 지원 OS·버전·알고리즘·문서 기준과 후속 기능을 명확하게 표시.

Core만 완성하거나 Python에서 테스트만 통과한 상태는 GUI 첫 버전 완료로 간주하지 않는다.

## 8. 개발 순서와 AI 작업 방식

1. 1차 범위와 미결정 항목 확인; 표준 버전·공식 벡터 목록 확보.
2. Core 입출력·오류 형식, 벡터 loader와 비교 기능 마련.
3. AES 등 알고리즘 하나와 최소 GUI를 연결하여 입력부터 결과까지 실행.
4. Windows 패키징을 조기에 시험하여 추가 설치 없는 실행 확인.
5. 나머지 legacy 알고리즘 추가 및 공식 전체 테스트 회귀 검증.
6. 결합 송신·수신 및 탭 기반 GUI의 형식 변환·오류·복사 기능 완성; Windows 배포 환경 검증.
7. Answer Set·비교 보고서·README 정리 후 첫 GUI 버전 릴리스.
8. 후속: 자료가 확보된 256-bit 계열 추가.
9. 후속: LLM adapter와 function calling/MCP 등의 연동 방식 결정.

### AI 개발 도구

- Coding agent / 환경: 작성자가 지정한 Codex sol6.1 / WSL.
- pstack / tstack: 활용 의향 있음. 구체적인 workflow는 agent가 개발 환경과 작업 규모에 맞춰 제안.
- PR 생성·push·merge 운영 방식: agent 판단을 요청한 상태. 저장소 환경과 지시 범위에 맞춰 적용.
- 모델 리뷰의 합의보다 공식 벡터의 실제 실행 결과를 완료 판단의 기준으로 삼는다.

### 후속 LLM 연동

- 자연어 요청 → 도구 호출 요청 → 실행 프로그램 → Core → 구조화된 결과 → LLM 설명.
- 계산과 PASS/FAIL 판정은 Python 프로그램이 수행한다.
- GUI와 동일한 코어를 호출하고, 직접 호출과 adapter 호출의 결과 일치를 확인한다.
- 전체 테스트는 요약과 실패 항목 중심으로 반환하고 상세 결과는 별도 조회하도록 설계할 수 있다.
- LLM 연결을 추가해도 GUI와 기존 공식 테스트는 유지한다.
